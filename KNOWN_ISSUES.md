# Известные проблемы PINDOS / Hammam

## RX virtio-net работает условно — причина не найдена

**LOAD-BEARING: без вызова `check_desc()` в `publish()` и `send()` RX не работает**
(0 из 5 прогонов, QEMU пишет `virtio: zero sized buffers are not allowed`).
Причина не найдена. Не удалять без 5 прогонов.

Симптомы при отсутствии вызова:

```
[ping] finished: 4 sent, 0 replied, 4 timed out
[diag] polls/s=61417 frames_rx=0 arp_replies=0 icmp_tx_left=256 tx_cap=4 status=0x07
qemu-system-x86_64: virtio: zero sized buffers are not allowed
```

С вызовом: `4 sent, 4 replied, 0 timed out`, stderr чистый, стабильно 5 из 5.

### Что проверено и НЕ является причиной

| Гипотеза | Результат проверки |
|---|---|
| Кэширование чтений компилятором | Опровергнута: volatile-переход (`9b06d54`) сам по себе не помог |
| SSE не сохраняется при переключении | Опровергнута: `objdump -d \| grep -c xmm` = 0 в обоих бинарях |
| Грязная память TX-кольца | Опровергнута: обе очереди обнулены, `AVAIL_IDX=0 USED_IDX=0` для q0 и q1 |
| Порядок инициализации (ARP до RX notify) | Опровергнута: пауза чинит в любом из трёх мест |
| Реальная запись нулевой длины драйвером | Опровергнута: `check_desc` ни разу не срабатывает (`ASSERT: 0`) |
| Устаревшая сборка как причина | Опровергнута: полная пересборка всех трёх крейтов с удалением `target/` даёт те же 0/5 |
| `ioeventfd` / доставка уведомлений | Опровергнута: `ioeventfd=off` на сломанной сборке даёт те же 0/5 |

### Что установлено фактически

- **Любая пауза в `init()` тоже лечит.** 200 000 `read_volatile` без единой печати
  даёт 5 из 5. Проверены три места: после настройки очередей до `DRIVER_OK`,
  после `DRIVER_OK` до первого `notify`, после первого `notify` до poll loop.
  Во всех трёх — результат одинаковый. Значит дело не в порядке, а в том, что
  устройство не успевает прочитать записи MMIO до нашего `notify`.
- **`check_desc()` не меняет данных.** Он не выполняет ни одной операции с
  кольцами, ни портов, ни печати в успешном пути. Тем не менее его присутствие
  полностью меняет результат. Это указывает на undefined behaviour, который
  компилятор случайно маскирует, либо на гонку, которую неявно снимает сам факт
  вызова функции.
- **QEMU-трассировка ненадёжна.** `-trace enable=virtqueue_pop,enable=virtio_queue_notify`
  в сломанной сборке даёт ровно одну строку `virtqueue_fill len=0 idx=0`, в рабочей —
  ноль строк, хотя `notify` вызывается многократно. Часть событий теряется при
  завершении по timeout. Номер очереди из `vq` расшифровать не удалось.
- **`status=0x07` не доказывает здоровье устройства.** Во всех сломанных прогонах
  статус остаётся `0x07` (DRIVER_OK, NEEDS_RESET не выставлен) при полностью
  неработающем RX.
- **`ioeventfd=off` не влияет.** На сломанной сборке (без `check_desc()`) пять прогонов
  из пяти с `-device virtio-net-pci,ioeventfd=off` дали тот же результат:
  `4 sent, 0 replied, 4 timed out` и `zero sized buffers are not allowed`.
  Значит дело не в том, как QEMU доставляет уведомление о завершении через ioeventfd,
  и не в нашем отсутствии поддержки eventfd.

### Следующие кандидаты (не проверены)

1. Read-after-write на MMIO-регистрах: после `outl(QUEUE_PFN)` читать `inl(QUEUE_PFN)`
   и ждать совпадения вместо немедленного `notify`.
2. Порядок записей: `len` в дескрипторе не должна записываться позже публикации
   в `avail`.
3. Синхронизация с вытеснением по таймеру во время инициализации очередей.
4. `fxsave`/`fxrstor` в `switch_context` — дыра реальна (SSE-регистры не
   сохраняются), но к текущему багу отношения не имеет, поскольку xmm не
   используется. Чинить отдельной задачей.

### Связанные известные ограничения

- `switch_context` не сохраняет FPU/SSE-состояние.
- `sys_dma_alloc` и I/O-порты доступны любому процессу без capability-проверки.
- Initramfs собирается во временный `Vec` на куче.

## Блокировка задач (3a): границы реализации

- `BLOCKED` и освобождение сырых `Arc` рассчитаны только на один CPU. `cli`
  защищает публикацию/сканирование/извлечение от локального timer IRQ; для SMP
  нужен отдельный протокол времени жизни указателей. NMI не вызывает `wake`.
- Kernel-код не вытесняется таймером: он может удерживать heap/physical lock.
  Kernel-потоки уступают CPU через `yield_now`/`block_current`; таймер продолжает
  считать время и выполнять `wake`. Userspace остаётся вытесняемым.
- В syscall IF сброшен через SFMASK: во время долгого syscall тики не приходят
  (пропущенные периоды не компенсируются), поэтому `sys_time` отстаёт от реального
  времени. Опрос COM1 тоже идёт из тика: аппаратный FIFO UART на 16 байт может
  переполниться до следующего опроса. Это отдельно от запрета вытеснять kernel-код
  при IF=1: в таком kernel-потоке timer IRQ продолжает обслуживаться.
- `syscall_entry` использует `r10` как scratch для user RSP и не восстанавливает
  его. Userspace inline asm должен объявлять clobber `rax`, `rcx`, `r10`, `r11`;
  старые wrappers проверены на это не полностью. Новый read-probe объявляет все
  четыре. Сохранение `r10` и аудит старых wrappers — отдельная задача.
- Timer IRQ не меняет размер `BTreeMap`: переключение заменяет `Arc` внутри
  существующего узла. Выбор сравнивает актуальные `vruntime` за O(n), а не O(log n).
  Разбуженные задачи попадают в дерево из idle/обычного scheduler-контекста.
- `wake` не освобождает `Dead`-слоты в IRQ: деструктор `Arc` может брать heap-lock.
  Очистка и возврат ссылки происходят при следующем обычном проходе scheduler.
- Регрессионный kernel-only тест: `python tools/test_sched.py` (три запуска QEMU).
  Он собирает `sched-test` во временной копии и синхронизирует только её
  `DATA_BOOT_VADDR`; штатные `boot.rs`, Cargo-артефакты и ISO не меняет.
  До первого запуска должны быть собраны release-бинари net-server и dealduck,
  поскольку initramfs по-прежнему встраивается, хотя userspace тест не запускает.

## Консольный read (3b)

- Syscall 6: читать можно только fd 0 с правом `readable` в таблице текущего
  процесса. `len=0` не спит; остальные чтения ждут хотя бы один байт и возвращают
  доступные данные (не более `len`). Wake-all требует повторной проверки условия.
- Кольцо SPSC имеет 256 слотов, полезная ёмкость — 255 байтов. При переполнении
  теряется новый байт: producer никогда не двигает consumer-owned `tail`.
  Несколько readers сериализованы IF=0 на UP, для SMP это не готово.
- Kernel echo отключён `CONSOLE_ECHO=false`. Приём и `wake` от константы не зависят.
- До включения SMAP нужны `stac`/`clac` вокруг копирования в user buffer (TODO
  находится в `sys_read`).
- Регрессии: `rustc --edition=2021 --test tools/test_console_ring.rs -o /tmp/pindos-ring-test`
  и `/tmp/pindos-ring-test`; `python tools/test_read.py` для настоящих userspace
  syscall, включая два конкурирующих reader и ping 4/4 без ввода. Второй тест
  собирает probe и временный initramfs/ISO отдельно, не устанавливая сервис в
  штатный образ. Release ELF net-server должен быть предварительно собран.
